# 诊断漏诊与报告展示修正

## 问题与边界

实际诊断使用 `/` 的 200 和健康检查代替 `/home` 的故障复现；Trace 使用不存在的服务名返回空集合，模型据此推测端口错配。页面将原始 JSON、Skill 和过程信息全部展开，掩盖结论。

本轮保留现有资源来源、审批与命令风险规则，不自动恢复故障、不修改业务部署。通用诊断流程与 Retail 业务排查说明分开，通用引擎不硬编码实验 IP、端口、服务名或注入真值。

## 已确认方案

1. 增加固定只读 HTTP 探测，逐次记录 URL、状态码、耗时、重定向、传输错误和响应摘要。错误页面、超时与健康端点不能互相替代。
2. 从 Tempo 发现真实 service.name，未知名称明确报错；已知服务查询为空也不证明健康。
3. 为实际工具观察分配证据 ID，模型提交结论引用证据。HTTP 故障的确认结论必须有对应业务 URL 的异常探测，缺口反馈给模型继续检查一次；仍不足就明确结束为未定位，禁止以健康壳页等弱证据确认根因。
4. Retail 专属 SOP 记录实际业务路由、依赖和只读故障开关检查方法，不预置当前故障值；按现有 Skill 匹配机制加载。
5. 报告优先展示问题、关键证据、影响、下一步与证据缺口。审批操作保持可见；原始日志、JSON、Skill、计划、节点默认折叠。

## 验证

- 200 壳页与异常业务页并存、超时、503、无效 Trace 名称、真实名称空结果、伪造/失败证据引用、证据不足后继续诊断与仍不足时停止。
- 原有网页审批、拒绝、重复执行和 SSH 补充回归。
- 用已注入故障的真实业务 URL 重新运行 dotOps，保留 Agent 工具记录与结论，不以人工查到的真值替代 Agent 诊断成功。

## 检查边界

HTTP 结论目前要求用户确认的完整 URL，不能把模型根据 SOP 猜出的页面自动认定为用户故障对象。缺少 URL 时允许收集部署事实，但最终要明确入口待确认。现有资源目录、CMDB 与图谱的入口映射不在本轮扩展。

证据检查验证来源、执行位置与必要观察，并拒绝未执行探测、重复页面探测代替原因、健康端点或空 Trace 代替原因。它不构成通用的因果证明器；页面使用「已有根因支持证据」而非宣称修复。

引用筛选只采纳真实有效观察。计划等过程记录不产生证据编号；额外的无效引用被排除并记录限制，不能凭空增加支持，也不能一票否决已具备业务复现与独立原因观察的结论。

- Linux 容器解释器 `/usr/local/bin/python`，67 项相关测试通过；最后摘要筛选调整再运行 14 项定向回归通过。前端 `tsc` 与 Vite Docker 构建通过。
- 真实诊断已通过 HTTP、UI 异常日志、catalog 商品响应、只读故障开关状态及 UI 客户端错误 Span，定位到 catalog 错误开关启用并返回 503，继而导致 `/home` 返回 500。
- 保存实际执行记录做引用回归，验证计划和失败的额外 Trace 查询不会冒充原因证据，也不会抹去已取得的独立正向证据。
